## Objetivo
Gravar em vídeo o jogo novo até o Pikachu e trocar os nomes padrão: o jogador passa a ter o
nome da IA que está jogando (CLAUDE, quando é o Claude Code) e o rival vira GEMINI. Depois,
publicar a primeira versão do site no GitHub Pages.

## Problemas e soluções

### 1. Vídeo da partida
- **Sintoma:** não havia como mostrar a partida, só screenshots soltas.
- **Causa:** o emulador só renderiza o último frame de cada ação.
- **Solução:** um script fora do pacote troca o `tick` do PyBoy por um que renderiza todo frame e
  manda o frame para o ffmpeg (60 fps, ampliado 4×). O `tick` do PyBoy é só leitura (Cython),
  então o script usa um objeto que repassa o resto para o PyBoy.
- **Evidência:** vídeo de 10.460 frames (2 min 54 s) até "received a PIKACHU", com a party final
  `[PIKACHU Lv5]`.

### 2. Digitar nomes na tela de nomes
- **Sintoma:** o jogo novo só sabia escolher os nomes prontos (YELLOW / BLUE).
- **Causa:** a tela de nomes é um teclado de letras, e não havia código para ele.
- **Solução:** `newgame.py`. O teclado está na `wTileMap` como texto (layout do
  `UpperCaseAlphabet` do pret), e o ▶ marca a letra atual. Para cada letra, o código lê a posição
  do ▶, anda até a letra, aperta A e no fim aperta START. Nomes aceitos: 1 a 7 letras A–Z
  (`PLAYER_NAME_LENGTH EQU 8` no pret, com o terminador). Nova tool MCP `new_game(player_name,
  rival_name="GEMINI")`, que valida os nomes antes de ligar o emulador.
- **Evidência:** `test_new_game_types_custom_names` (ROM): jogador CLAUDE, rival GEMINI, no
  quarto com controle livre. No vídeo, o Oak diz "His name is GEMINI!".

### 3. O site não existia
- **Sintoma:** a Fase 1 tinha código e diário, mas nenhuma página. O GitHub estava parado na
  sessão 0 (7 commits sem push).
- **Causa:** o push esperava autorização, e o site ainda não tinha sido começado.
- **Solução:** site estático em `site/` (HTML, CSS e JS sem build), com 5 idiomas e suporte a
  RTL no árabe:
  - visão geral das camadas;
  - a tabela de tempos do andar contra a malha fechada;
  - o decodificador RAM → estado com 4 snapshots;
  - uma sessão MCP real animada;
  - a linha de base com os marcos;
  - este diário.

  Os dados vêm de código do pacote:
  - `yellow-baseline` roda o script até o Pikachu e gera os marcos, os snapshots e o vídeo;
  - `yellow-site-data` gera o diário e grava a sessão MCP real.

  Um workflow publica o site no Pages a cada push.
- **Evidência:** `site/data/*.json`; a mesma linha de base deu os mesmos 11.470 frames que o
  script avulso (determinismo).

### 4. Achado: no catch do Oak, o nome do jogador vira PROF.OAK
- **Sintoma:** o snapshot da batalha do Oak tem `player_name: "PROF.OAK"`.
- **Causa:** o jogo troca o nome do jogador durante a demonstração de captura. É o próprio jogo,
  não um erro de leitura.
- **Solução:** nenhuma; fica visível no decodificador do site.
- **Evidência:** `site/data/snapshots/oak_battle_menu.json`.

## Decisões
- O nome do jogador é o da IA que joga. Nos benchmarks da Fase 2, cada modelo joga com o seu nome,
  e o rival continua GEMINI.
- O vídeo saiu do script avulso para o pacote: `Emulator.on_frame` recebe cada frame, e o
  `yellow-baseline --video` grava o MP4.
- Os snapshots antigos, que vinham de saves locais, foram trocados pelos da linha de base. Agora
  todos se regeneram só com a ROM.
- O diário aparece em pt-BR em todos os idiomas, com um aviso. A interface está nos 5 idiomas.
